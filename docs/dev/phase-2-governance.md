# EduFDE 第二阶段工程治理

> 本文件规定第二阶段开发会话的治理方式。第一阶段原始治理文件已归档，本阶段继续使用现有 `docs/dev` 体系，但默认上下文保持轻量。

## 一、阶段目标

第二阶段目标是在不破坏终局架构地基的前提下，把已验证的 MVP 和学生端第一轮产品形态继续打磨为更真实的教学体验。

核心方向：

- 减少同质化表单。
- 强化每个阶段独有任务形态。
- 补强 AI 行为、Rubric 证据和 Artifact 结构。
- 补齐黄灯债务、项目档案袋、学习画像和教师判断闭环。
- 将后端重复阶段逻辑逐步抽象为共享能力。

## 二、默认上下文策略

每次会话默认读取：

1. `AGENTS.md`
2. `docs/README.md`
3. `docs/dev/current-context.md`
4. `docs/dev/progress.md`
5. `docs/dev/decisions.md`
6. 本次任务相关的 v2.0 设计文档

不默认读取：

- 第一阶段完整 `progress.md`。
- 第一阶段完整 `decisions.md`。
- MVP 收口审查。
- student2 走查材料。
- 阶段性复盘全文。

这些材料已经归档，只有需要追溯时才读取。

## 三、会话边界

每个会话只处理一个可独立验证的切片。

推荐切片类型：

- 一个阶段的一个前端交互区。
- 一个阶段的一个后端接口或服务规则。
- 一个 AI 评审输出结构。
- 一个 Artifact 结构或展示规则。
- 一个黄灯债务状态流转。
- 一个共享后端阶段运行能力。

避免：

- 一次性处理多个阶段。
- 同时做教师后台、权限、Dify、评分和学习画像。
- 在功能切片中顺手大规模重构无关文件。
- 为了“干净”删除仍被当前流程依赖的兼容接口。

## 四、第二阶段优先级

### P0：阶段一项目实战模式

目标：

- 正式客户拜访更像真实需求访谈。
- 多轮上下文稳定。
- 右侧线索、待追问问题和拜访整理能帮助学生形成正式证据。
- 问题发现总结和综合评估能稳定成为阶段二输入。

### P1：AI 评审结构化

目标：

- 阶段二至阶段五减少 fake 风格输出。
- 明确红灯、黄灯和通过判断。
- 评审输出引用学生产物证据。
- 评审结果能进入 Artifact 和后续阶段门禁。

### P1：黄灯债务闭环

目标：

- 学生能确认黄灯。
- 后续阶段能看到待回应黄灯。
- 学生能用产物回应黄灯。
- AI 或教师能判断清除、继续携带或豁免。

### P2：后端阶段运行通用能力

目标：

- 抽取阶段作用域查询、阶段可写校验、上一阶段完成校验、最新产物查询、Rubric 快照和完成解锁逻辑。
- 降低阶段一至阶段五服务重复。

### P2：正式教师后台与课程权限

目标：

- 用课程成员模型替换 `courses.created_by_user_id` 临时边界。
- 正式教师后台支持课程、学生进度、产物查看、批改和评分。

## 五、文档更新规则

每次实现会话结束时：

- 更新 `docs/dev/progress.md`。
- 如产生长期有效决策，更新 `docs/dev/decisions.md`。
- 如形成阶段级交接材料，可创建日期化文档，但不要让它成为默认上下文。
- 如文档成为历史材料，应归档到阶段目录，不要长期堆在 `docs/dev` 根目录。

## 六、归档规则

归档目录：

- `docs/dev/archive/phase-1-productization-archive/`

归档原则：

- 原文保留。
- 当前入口路径保留。
- 当前默认上下文压缩。
- 归档文件只用于追溯，不用于每次会话默认读取。

未来每完成一个明显阶段，可以新建新的归档目录，例如：

```text
docs/dev/archive/phase-2-<name>-archive/
```

但不应频繁切换治理入口路径。
