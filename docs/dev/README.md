# EduFDE 开发治理说明

本目录用于保存长期开发上下文，避免依赖单个聊天会话记忆。

目标是让每个 Codex 会话都能短、准、可恢复。

当前项目已经进入产品化精修与真实能力迭代阶段。后续治理重点不只是记录“完成了哪些页面和接口”，还要记录每个页面 / 阶段精修时形成的产品体验边界、后端约束、AI 行为、Artifact 结构和验证结论。当前正在精修阶段一工作台；教学引导模式第一轮功能体验已阶段性收口，下一步重点切换为阶段一项目实战模式，围绕正式客户拜访、拜访间整理、问题发现总结、综合评估和阶段二输入证据链继续迭代。

## 一、文件说明

- `progress.md`  
  记录当前实现状态、已完成模块、验证结果和下一步建议任务。

- `decisions.md`  
  记录长期有效的产品和工程决策。凡是会影响后续开发的选择，都应写入这里。

- `session-handoff-template.md`  
  用于结束一个开发会话时做交接，降低下一个会话的上下文成本。

- `module-prompt-template.md`  
  用于启动具体模块开发会话的提示词模板。

## 二、会话纪律

每个开发会话只处理一个边界清晰的目标。

合适的会话范围：

- 初始化后端应用和 Docker Compose。
- 实现 AI Gateway 模块。
- 实现阶段一后端 API。
- 实现阶段一学生端界面。
- 精修登录页、课程列表、实验项目主页或某一个阶段工作台。
- 为某一个阶段补强 Artifact schema、AI Prompt、service 校验或错误处理。

不合适的会话范围：

- 一次性构建整个 MVP。
- 一次性实现全部五个阶段。
- 在添加功能时顺手大规模重构无关模块。
- 同一轮同时精修多个页面、接真实 Dify、改权限模型和做教师后台。

## 三、新会话必须阅读的上下文

每个开发会话开始时，应让 Codex 阅读：

1. `AGENTS.md`
2. `docs/README.md`
3. `docs/dev/progress.md`
4. `docs/dev/decisions.md`
5. 本次任务相关的 v2.0 设计文档

## 四、每个会话的结束要求

每个实现会话结束时，应明确：

- 修改了哪些文件
- 做了哪些验证
- 有哪些未验证区域
- 是否更新了 `progress.md`
- 是否需要更新 `decisions.md`
- 下一步推荐任务是什么
