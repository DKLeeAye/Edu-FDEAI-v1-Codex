## 二、原型实现形态

这批原型不是生产前端工程，而是高保真静态原型；但它是本轮升级后的正式产品体验基准。

当前存在两种页面形态：

1. 完整静态 HTML 页面  
   用于官网、登录页、学生首页、实验详情、阶段一至阶段五核心学生流程。页面内包含布局、文案、表单、局部 JavaScript 和 `localStorage` 模拟状态。

2. `app.js` 配置式渲染页面  
   用于教师工作台、课程配置、实验包库、课中监控、AI 评审、部署管理等页面。页面通过 `renderPage({...})` 传入配置，由通用 `panel`、`table`、`workflow`、`evidence` 等模板渲染。

工程迁移含义：

- 学生端阶段页适合拆为真实 React 组件和业务页面。
- 教师 / 管理页适合先提炼为后台通用组件和页面配置模型。
- `localStorage` 只代表原型交互状态，生产实现必须替换为后端状态、Artifact、阶段记录、AI 调用记录和教师审计记录。
- 不应直接整体迁移 `app.css`，应抽取设计 token、布局模式和组件样式到现有 Tailwind / React 组件体系。
- 页面流程和体验分割以 Open Design vNext 为准。现有产品中与新版设计冲突的旧流程应迁移、合并或退为兼容入口，而不是在正式产品中并列保留。

## 四、与当前实现的主要差异

### 4.1 产品体验差异

新版原型明显从“功能工作台”升级为“教学任务工作区”：

- 阶段一从聊天记录升级为“访谈实战 + 实时线索 + 记录抽屉 + 整理提交”。
- 阶段二从三份文档保存升级为“章节式证据驱动报告工作台”。
- 阶段三从知识工程决策升级为完整 RAG 学习路径：数据源、质量、清洗、结构、分块、向量、召回、引用、测试、边界。
- 阶段四从提交 Dify 信息升级为“知识库创建、文件上传、分段清洗、索引检索、Chatflow、Prompt、Preview、发布”的 12 步正式构建记录。
- 阶段五从材料提交升级为“交付文档章节工作台 + 验收确认 + 项目档案袋归档”。
- 教师端从基础进度视图升级为课程运行、课中监控、红黄灯债务、AI 待确认和班级复盘。

### 4.2 工程契约差异

当前后端已具备统一 Artifact、阶段服务、AI Gateway、AI 调用日志、基础教师进度和学习画像。新版原型会倒逼以下增强：

- Artifact 类型更细：尤其是阶段三 10 个 RAG 过程产物、阶段四 Dify 构建细项、阶段五章节级交付文档。
- AI 评审更结构化：需要 `verdict`、红灯 / 黄灯 / 通过、Rubric 维度、证据引用、错误处理、教师确认或覆盖。
- 黄灯债务需要闭环：原型多处把黄灯风险作为后续阶段输入，不能只停留在文本提示。
- 项目档案袋需要后端聚合能力：当前前端聚合 Artifact 的方式不足以支撑最终归档、导出和教师复核。
- 教师端需要课程成员权限模型：原型中的教师工作台和课中监控不能长期依赖 `courses.created_by_user_id`。

## 五、建议的数据与 Artifact 映射

### 阶段一

阶段一正式产品形态以 Open Design vNext 为准，不再保留旧版“教学引导模式 / 项目实战模式”双入口分割。

新版阶段一应实现为连续流程：

```text
导学方法页
→ AI 客户访谈工作区
→ 访谈记录整理与阶段提交
→ 阶段二输入证据链
```

其中 `06-interview-guide.html` 是新版正式流程中的导学页，不等同于旧六关卡教学引导模式。旧六关卡训练数据如继续保留，只能作为遗留兼容或独立训练记录，不进入正式产品主路径，也不作为阶段二输入。

新版阶段一需要至少沉淀：

- 正式访谈轮次：客户原话、学生问题、AI 客户回复、AI 调用日志 ID。
- 访谈洞察快照：已识别需求、客户痛点、项目关键信息、待追问问题。
- 访谈整理：客户原话摘录、已确认事实、待确认问题、需求理解草稿、边界判断。
- 阶段一综合评估：AI 评估、规则检查、进入阶段二建议。

现有 `StageOneVisitNotesPayload`、`StageOneSummaryPayload` 和评估接口可作为基础，但需要补强“新版访谈、多轮上下文、线索和待追问问题”的结构，并把旧双模式 UI 迁移为新版三步流程。

### 阶段二

原型的 6 章工作台应与当前三份正式文档对齐：

- 需求分析报告：项目背景与客户问题、需求分析。
- 可行性研究报告：可行性研究、能力边界。
- 总体技术方案：总体技术方案、验收与风险说明。

建议前端可以采用 6 章编辑体验，后端 Artifact 仍保持三份正式文档，并额外保存章节草稿 / 章节评审过程。

### 阶段三

原型将阶段三拆为 10 个 RAG 决策环节，建议按过程 Artifact 逐步落地：

1. 数据源识别。
2. 数据质量评估。
3. 清洗与预处理策略。
4. 知识结构设计。
5. 分块策略。
6. 向量化与存储配置。
7. 召回策略。
8. 回答生成与引用策略。
9. 召回测试报告。
10. 风险边界声明。

这些过程产物最后应汇总为阶段三正式“知识工程决策文档”和阶段四输入，而不是把 10 个页面都视为独立最终成果。

### 阶段四

原型已经明确阶段四正式记录字段：

- Dify 应用名称与用途。
- 知识库名称和创建方式。
- 上传文件清单。
- 分段与清洗配置。
- 索引与检索配置。
- 检索节点变量关系。
- 边界分支规则。
- Prompt 摘要。
- 异常路径 / 转人工模板。
- 节点连线与变量传递。
- Preview 预检记录。
- 发布链接和访问说明。

当前可先作为手工回填 Artifact 落地；真实 Dify API、文件解析和向量库后续再接入。

### 阶段五

原型阶段五有两个核心产物：

- 交付说明文档：6 章结构，章节级 AI 检查和保存。
- 交付验收记录：交付包清单、模拟客户追问、验收结论、维护责任和归档依据。

这些可以映射到现有阶段五交付文档、验收包和运维说明，但建议统一成“交付文档章节 + 验收签收 + 运维维护说明”的结构。

- 学生确认黄灯。
- 后续阶段能看到并回应黄灯。
- AI 或教师判断清除、继续携带或豁免。

- 原型阶段三深度很大，一次迁移 10 页风险过高。

## 七、迁移原则

1. 不直接把静态 HTML 当生产页面接入。
2. 不整体复制 `app.css` 到生产样式，应抽取设计 token、布局模式和组件样式。
3. 不把 `localStorage` 当业务状态，所有正式阶段状态必须进入后端。
4. 不为了页面效果绕开 AI Gateway、Artifact、Rubric、课程作用域和教师最终判断权。
5. 每个切片都要保留当前可运行闭环，避免一次性替换五阶段主流程。
6. 教师 / 管理页面先作为后续实现输入，学生主路径和阶段一 P0 优先；但最终实现时同样应对齐 Open Design vNext，而不是复用旧教师端联调视图。
7. 与 Open Design vNext 冲突的旧产品流程不在正式产品中并列保留。可短期保留兼容接口和迁移辅助入口，但不能作为目标体验。
7. 官网 `index.html` 暂不进入第一轮主线，除非明确启动对外官网开发。

## 八、建议的第一项开发任务

建议下一项正式开发任务定为：

```text
Open Design vNext 学生主路径壳层升级第一切片：
登录页、学生首页、制造业质检实验详情页和五阶段入口导航接入现有后端课程 / 实验会话 / 阶段状态。
```

如果希望更贴合当前 P0 治理优先级，也可以跳过壳层，直接进入：

```text
阶段一新版访谈流程升级第一切片：
以 06-interview-guide.html、06-interview-lab.html 和 06-interview-submit.html 为体验目标，替换旧教学引导 / 项目实战双入口，升级 AI 客户访谈、多轮上下文、访谈线索、待追问问题和阶段二输入证据链。
```

推荐优先级：先做学生主路径壳层升级，再立刻进入阶段一 P0。原因是壳层切片能低风险验证新设计体系在现有 Next.js 工程中的落地方式，并为阶段一专注页面提供可复用的导航、按钮、状态、侧栏和视觉 token。
