# EduFDE · 阶段二详细设计文档
# 需求拆解与分析

> 版本：v1.0 | 状态：已达成共识 | 日期：2026-04-28

---

## 一、阶段定位

### 教学目标

让学生掌握将模糊的客户访谈信息加工成结构化项目文档的能力，核心是训练三个递进的思维能力：

1. **去噪**：区分客户表达中的真实需求、情绪表达、表面现象
2. **建结构**：把散乱信息归入标准框架，形成清晰的需求全景
3. **判断可行性**：结合数据现状、技术边界、ROI做出是否值得做、能不能做的判断

### 阶段在整体流程中的位置

```
阶段一输出（访谈记录）
         ↓
    【阶段二：需求拆解与分析】← 本文档范围
         ↓
┌────────┬─────────┬─────────┐
↓        ↓         ↓         ↓
需求文档  可行性报告  技术架构   → 阶段三四五各自直接使用
                   文档（平台级）
```

### 阶段二的枢纽角色

阶段二是整个项目的"枢纽"——阶段一产出原材料，阶段二把原材料加工成后续三个阶段各自能直接使用的施工图纸。

**先建地图，后走地形：**

```
阶段二：画地图（整体认知）
  需求文档        → 确定去哪里
  可行性报告      → 确定能不能去
  技术架构文档    → 确定走哪条路（平台级选择）
       ↓
阶段三入口：知识库方案细化
阶段四入口：智能体架构细化
阶段五入口：部署方案细化
```

学生在阶段二建立整体认知，进入后续阶段时知道自己当前操作在整个项目中的位置，不会迷失。

## 二、核心体验形态：滚动推进

阶段二不采用阶段一的关卡制，而是**滚动推进模式**。

```
写一节 → 被AI追问 → 修改完善 → 继续写下一节
  ↑_________________________________↓
              反复迭代
```

三个文档串行完成，每个文档内部是滚动推进，文档之间有AI评审节点拦截。

**串行逻辑：**
- 需求文档写完 → AI评审通过 → 才能开始可行性报告
- 可行性报告完成 → AI评审通过 → 才能开始技术架构文档
- 技术架构文档完成 → 阶段二结束，进入阶段三

后面的判断依赖前面的结论，不能并行，也不能跳过。

## 三、AI评审机制

### 3.1 AI评审的两种角色

**主要风格：严格的技术评审官（A）**

直接、精准、不留情面，用精确的追问逼迫学生把模糊表述变成清晰判断：

> "你写的核心需求是'提升质检效率'，这个表述过于宽泛。请明确：你指的是漏检率、质检速度还是人力成本？三者的技术路线完全不同。"

**兜底风格：引导式的资深同事（B）**

当学生被同一个问题连续追问两次仍未答对时，自动切换为引导风格：

> "你写到了质检效率，这个方向感觉对。我有个问题帮你想得更清楚一点——客户上次提到漏检率10%，这个数字背后具体是什么场景？是某一类零件特别容易漏检，还是整体都有问题？"

**切换逻辑：**
```
同一问题追问次数 = 1次 → 风格A
同一问题追问次数 = 2次 → 风格A（加强版，更具体的指向）
同一问题追问次数 ≥ 3次 → 切换风格B，给出引导性提示
```

### 3.2 文档内滚动追问

学生每完成文档的一个小节，AI评审立即介入追问，不等整个文档完成。

**追问触发条件：**
- 表述过于宽泛（无法指导后续技术决策）
- 与阶段一访谈记录存在矛盾
- 关键维度缺失
- 判断没有依据支撑

**追问不触发条件：**
- 表述清晰、有具体依据
- 与访谈记录一致
- 逻辑自洽

### 3.3 文档间强制评审节点

每个文档完成后，AI进行整体评审，分两个等级：

```
【红灯】必须返工，无法进入下一文档
────────────────────────────────
· 核心需求方向判断错误
· 客户痛点完全没有提炼出来
· 文档存在明显的内部逻辑矛盾
· 关键信息缺失超过阈值

【黄灯】警告但可选择继续
────────────────────────────────
· 信息有遗漏但方向正确
· 某个维度描述不够具体
· 表达清晰度不足但意思正确

黄灯处理机制：
· 学生必须阅读并确认警告内容
· 系统记录所有黄灯问题
· 这些"债"会在后续阶段以更高难度形式出现
  （例：知识库阶段发现数据质量问题，追溯到可行性报告
   没有充分评估数据现状）
```

**黄灯的债务机制**是阶段二和后续阶段联动的关键设计——学生能感受到"阶段二写得不认真，阶段三就会更难"这个真实规律。

## 四、三个输出文档详细设计

### 4.1 文档一：需求文档

**定位：** 写给客户看，语言要客户能理解，聚焦业务问题和解决方向，不涉及技术细节。

**渐进式框架显现规则：**
- 第一次完成阶段二：框架完全可见，每项有"为什么要想这个"的说明
- 第二次：只显示一级标题
- 第三次及以上：空白页，学生自己构建结构

**文档结构：**

```
一、项目背景
    1.1 客户基本情况
        [客户公司规模、行业、业务模式的简要描述]
    1.2 当前业务现状
        [现有流程是怎么运转的，关键数据]

二、核心问题与痛点
    2.1 主要痛点
        [具体的、有量化描述的痛点，不是情绪化表达]
    2.2 问题根因分析
        [为什么会有这些痛点，背后的原因]
    2.3 问题的业务影响
        [这些问题造成了什么损失或风险]

三、需求目标
    3.1 核心需求
        [客户最想解决的是什么，精确到具体场景]
    3.2 期望效果
        [解决之后业务层面应该达到什么状态]
    3.3 验收标准初稿
        [怎么判断项目成功了，客户认可的标准]

四、约束条件
    4.1 时间约束
    4.2 预算范围（如已知）
    4.3 组织与人员约束
    4.4 现有系统约束
```

**AI评审重点追问维度：**
- 痛点是否具体到场景（"效率低"不够，要"哪个环节、多低、影响什么"）
- 需求目标是否和痛点直接对应（不能痛点是A，目标却是B）
- 验收标准是否可测量（不能只说"客户满意"）
- 约束条件是否如实反映访谈中获取的信息

---

### 4.2 文档二：可行性报告

**定位：** 写给内部团队看，核心是判断三件事：数据基础够不够、技术上能不能做、投入产出值不值。

**文档结构：**

```
一、数据可行性
    1.1 数据来源盘点
        [有哪些数据，在哪里，谁管]
    1.2 数据质量评估
        [数据的完整性、准确性、可用性判断]
    1.3 数据差距分析
        [要做这个AI项目，现有数据够不够？差什么？]
    1.4 数据可行性结论
        [可行 / 需要补充 / 不可行，给出判断依据]

二、技术可行性
    2.1 AI能解决的部分
        [明确界定AI介入点，不夸大也不缩小]
    2.2 AI不能解决的部分
        [边界在哪里，为什么]
    2.3 技术风险点
        [可能遇到的技术挑战]
    2.4 技术可行性结论
        [可行 / 有条件可行 / 不建议，给出判断依据]

三、ROI初步判断
    3.1 预期收益估算
        [解决问题后的业务价值，尽量量化]
    3.2 实施成本估算
        [时间、人力、资金的大概范围]
    3.3 ROI结论
        [值得做 / 有条件值得做 / 不建议，给出判断依据]

四、综合可行性结论
    [基于以上三个维度的综合判断，给出明确建议]
    [建议进行 / 建议调整范围后进行 / 建议暂缓]
```

**AI评审重点追问维度：**
- 数据质量评估是否基于访谈中获取的真实信息（不能凭空假设数据很好）
- AI能解决的边界是否合理（常见错误：过度承诺AI能力）
- 结论是否有依据支撑（不能只有结论没有推理过程）
- 三个维度的结论是否相互一致（不能数据不可行但技术结论却说可行）

**与需求文档的联动：**
可行性报告中发现的约束和风险，如果与需求文档中的约束条件矛盾，AI评审会触发跨文档追问，要求学生回头修正需求文档。

---

### 4.3 文档三：技术架构文档（平台级）

**定位：** 写给自己后续执行用的整体技术路线图，平台级选择题为主，不要求深度技术细节（细节在三四五阶段各自细化）。

**核心设计：选择题 + 选择依据说明**

学生不需要凭空设计架构，而是基于项目情况在平台提供的选项中做出选择，并说明选择原因。

**文档结构：**

```
一、整体技术路线
    [系统自动根据后续选择生成可视化架构图]

二、知识库方案选择
    选项A：文档型知识库
           适用：数据主要是PDF、Word等非结构化文档
    选项B：结构化数据知识库
           适用：数据主要在数据库、Excel等结构化形式
    选项C：混合型知识库
           适用：两种数据都有

    → 学生选择：[  ]
    → 选择依据：[学生填写，说明为什么选这个]

三、智能体构建方式选择
    选项A：对话型智能体
           适用：主要交互方式是问答、咨询
    选项B：工作流型智能体
           适用：有明确的多步骤业务流程需要自动化
    选项C：混合型
           适用：既有对话交互又有流程自动化

    → 学生选择：[  ]
    → 选择依据：[学生填写]

四、数据流向设计
    [系统根据以上选择自动生成标准数据流向图]
    [学生确认或提出修改意见]

五、部署方式初步选择
    选项A：云端SaaS部署
    选项B：私有化部署
    选项C：混合部署

    → 学生选择：[  ]
    → 选择依据：[学生填写]

六、技术风险备注
    [学生填写：预见到的技术风险和应对思路]
```

**选项说明设计原则：**
- 每个选项都有简洁的"适用场景"说明
- 不使用过于技术化的语言
- 选项之间的区别要对学生直观可感

**AI评审重点追问维度：**
- 选择与项目实际情况是否匹配（选了文档型知识库但项目数据明显是结构化的）
- 选择依据是否基于项目特点（不能只写"感觉这个好"）
- 各项选择之间是否一致（部署选了私有化但后面又假设有云端资源）

## 五、界面设计要点

### 5.1 整体布局

```
┌─────────────────────────────────────────────────────────┐
│  顶部：阶段进度 | 当前文档（1/3）| 当前文档完成度         │
├──────────────────┬──────────────────────────────────────┤
│                  │                                      │
│  左侧面板        │  右侧：文档编辑区                     │
│                  │                                      │
│  · 阶段一产出    │  上半部分：当前编辑节                  │
│    访谈记录      │  （渐进式框架 / 空白）                 │
│    （可折叠）    │                                      │
│                  │  下半部分：AI评审对话区                │
│  · 当前文档      │  （追问与回应的来回记录）              │
│    完成进度树    │                                      │
│                  │                                      │
│  · 框架说明      │                                      │
│   （第一次可见） │                                      │
│                  │                                      │
├──────────────────┴──────────────────────────────────────┤
│  底部：保存草稿 | 提交本节 | 查看AI评审历史               │
└─────────────────────────────────────────────────────────┘
```

### 5.2 关键交互细节

**阶段一访谈记录的可见性：**
- 始终在左侧面板可访问，可折叠展开
- 学生在写文档时可以随时翻阅对照
- 系统会在AI追问时自动高亮相关的访谈片段（"你在第一次拜访中，客户提到过..."）

**文档编辑区：**
- 支持富文本编辑
- 自动保存草稿，防止意外丢失
- 每个小节有独立的"提交本节"按钮，提交后触发AI追问
- 已通过AI评审的节用绿色标记，存在黄灯警告的节用黄色标记

**AI评审对话区：**
- 追问以对话气泡形式呈现（AI评审官 vs 学生回应）
- 学生可以直接在对话区回应追问，也可以修改上方文档后重新提交
- 追问历史完整保留，学生可以看到自己思维演进的过程

**文档间评审节点：**
- 以全屏覆盖层形式呈现，强制学生阅读
- 红灯：明确标出必须修改的内容，修改完才能关闭
- 黄灯：列出所有警告，学生逐条确认后可继续

## 六、阶段二输出物汇总

学生完成阶段二后，产出以下内容：

```
┌─────────────────────────────────────────────────────┐
│  阶段二完成包                                        │
├─────────────────────────────────────────────────────┤
│                                                     │
│  文档一：需求文档                                    │
│  · 完整度评级：[完整 / 基本完整 / 有遗漏]            │
│  · 黄灯警告列表（如有）                              │
│                                                     │
│  文档二：可行性报告                                  │
│  · 可行性结论：[可行 / 有条件可行 / 不建议]          │
│  · 黄灯警告列表（如有）                              │
│                                                     │
│  文档三：技术架构文档                                │
│  · 技术路线选择摘要                                  │
│  · 自动生成的架构图                                  │
│                                                     │
│  阶段二综合评分：[X分]                               │
│  累计黄灯数量：[N条]（将影响后续阶段难度）            │
│                                                     │
└─────────────────────────────────────────────────────┘
```

### 进入阶段三的条件
- 三个文档均通过AI评审（无红灯）
- 黄灯警告均已确认（不要求清零，但要求知晓）
- 技术架构文档中的知识库方案选择，直接作为阶段三的初始配置

## 七、阶段二与前后阶段的联动设计

### 与阶段一的联动
- 阶段一的访谈记录是阶段二的唯一输入源
- AI评审会主动引用访谈记录中的具体片段来质疑或支持学生的文档内容
- 如果学生的文档内容与访谈记录明显矛盾，触发红灯

### 与阶段三四五的联动
```
技术架构文档中的选择 → 直接预填阶段三知识库方案配置
可行性报告中的风险点 → 在对应阶段入口提示（"你在可行性报告中提到了数据质量风险，
                        进入知识库搭建阶段后请重点关注数据清洗环节"）
黄灯债务 → 在相关阶段以更高难度形式出现，让学生感受到前期工作质量的影响
```

## 八、待确认事项

> 阶段二设计已达成共识，以下为开发阶段需进一步细化的技术决策

1. **渐进式框架的触发条件**：是按完成次数，还是按评分达标与否来决定框架显现程度？
2. **黄灯债务的具体体现方式**：在后续阶段如何自然地呈现债务，不让学生感到被惩罚，而是感到"这是真实项目的因果"？
3. **跨文档追问的深度**：当可行性报告发现问题需要修改需求文档时，允许学生跳回需求文档修改吗？还是记录为黄灯继续往下走？
4. **AI评审官的身份设定**：是否需要给AI评审一个具体的角色人设（如"公司技术总监"），还是保持中性的系统评审身份？
