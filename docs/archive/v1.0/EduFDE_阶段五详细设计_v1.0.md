## 一、阶段定位

### 教学目标

让学生完成从"本地可运行"到"真实可交付"的最后一跳——把阶段四做好的智能体部署到真实服务器上，让系统稳定跑起来，完成对客户的交付。

### 核心教学理念

**部署不是收尾工作，是交付能力的核心体现。**

在真实项目里，客户最关心的不是方案有多漂亮，而是系统能不能稳定运行。阶段五要培养的是这种"交付意识"——对自己部署的系统负责，能跑起来，出了问题知道怎么查。

### 教学边界

```
必须教（核心交付能力）：
  · 服务器基础操作（Linux命令行不恐惧）
  · Docker容器化（标准化打包）
  · 云服务器部署并启动服务
  · 服务健康验证
  · 环境变量和配置管理

应该教（让系统稳住）：
  · 服务挂掉后自动重启（进程守护）
  · 基础日志查看（出问题怎么定位）
  · Nginx反向代理（正常的访问地址）

不教（超出范围）：
  · CI/CD自动化部署
  · Kubernetes容器编排
  · 监控告警系统
  · 高可用和负载均衡
```

### 阶段在整体流程中的位置

```
阶段四输出（本地可运行的AI应用）
         ↓
   【阶段五：部署交付验收】← 本文档范围
         ↓
   项目完成，输出学习画像
```

## 三、低代码路径（Dify）阶段五

### Part A：部署认知

**教学目标：**
让Dify路径的学生了解私有化部署的概念和必要性，建立"云端部署不是唯一选项"的认知，为将来遇到私有化需求时不完全陌生做准备。

**内容设计：**

```
为什么需要私有化部署？
  · 数据安全要求：金融、医疗、政府客户不允许数据出域
  · 合规要求：某些行业有数据本地化的法规要求
  · 性能要求：内网部署延迟更低
  · 成本要求：大规模使用时自建比SaaS更经济

Dify云端 vs 私有化部署对比：
┌──────────────┬─────────────┬─────────────────┐
│              │ Dify云端     │ 私有化部署       │
├──────────────┼─────────────┼─────────────────┤
│ 部署难度     │ 无需操作     │ 需要运维能力     │
│ 数据位置     │ Dify服务器   │ 客户自己服务器   │
│ 维护责任     │ Dify负责     │ 自己负责         │
│ 定制灵活性   │ 有限         │ 完全可控         │
│ 适用场景     │ 快速验证     │ 正式生产环境     │
└──────────────┴─────────────┴─────────────────┘

私有化部署需要什么？
  · 一台服务器（云服务器或本地服务器）
  · 安装Docker和Docker Compose
  · 下载Dify的私有化部署包
  · 配置环境变量（数据库、密钥等）
  · 启动服务并验证

[观看私有化部署演示视频]（约10分钟，只看不做）
```

### STEP 2：Docker容器化

**教学目标：**
理解Docker的核心概念，能够为自己的LangGraph应用编写Dockerfile并完成本地构建测试。

**核心概念：**

```
为什么用Docker？
  没有Docker的问题：
  "在我电脑上能跑，在服务器上跑不了"
  → 环境不一致：Python版本不同、依赖版本不同、系统不同

  Docker的解决方案：
  把应用和它需要的所有环境打包在一起
  这个包（镜像）在任何安装了Docker的地方都能运行
  → 一次打包，到处运行

核心概念对照：
  镜像（Image）：应用的打包文件，类似安装包
  容器（Container）：镜像运行起来的实例，类似进程
  Dockerfile：描述如何构建镜像的配置文件
  docker build：根据Dockerfile构建镜像
  docker run：启动一个容器
```

**Dockerfile模板（含填空）：**

```dockerfile
# 基础镜像：使用Python 3.11精简版
FROM python:3.11-slim

# 设置工作目录
WORKDIR /app

# 学生需要填写：把requirements.txt复制到容器里
# 提示：COPY 源文件 目标路径
COPY _____________ .

# 安装Python依赖
RUN pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple

# 学生需要填写：把项目代码复制到容器里
# 提示：把当前目录所有文件复制到容器的/app目录
COPY _____________ .

# 设置环境变量（API Key等从外部传入，不写在这里）
ENV PYTHONUNBUFFERED=1

# 学生需要填写：启动命令
# 提示：你的应用入口文件是main.py，用python运行它
CMD ["____________"]

# [查看原理：为什么这样写Dockerfile ▼]
# · FROM：选择基础环境，python:3.11-slim是官方精简版
# · WORKDIR：容器内的工作目录，后续命令都在这里执行
# · 先复制requirements.txt再安装依赖，是为了利用Docker缓存层
#   （只要依赖没变，这一层就不用重新构建，加快build速度）
# · ENV PYTHONUNBUFFERED=1：让Python日志实时输出，不缓冲
# · CMD：容器启动时执行的命令
```

**本地构建测试：**

```bash
# 在项目根目录执行
docker build -t edu-fde-agent .

# 本地测试运行
docker run -p 8000:8000 \
  --env-file .env \
  edu-fde-agent

# 验证：在另一个终端测试服务是否响应
curl http://localhost:8000/health
```

**验收标准：**
本地docker build成功，docker run后服务可以响应即完成。

### STEP 3：服务器部署

**教学目标：**
将容器化的应用部署到云服务器上，实现从本地到服务器的完整迁移。

**操作流程：**

```
方式一：代码上传到服务器（推荐）

本地操作：
  # 把项目打包
  tar -czf edu-fde-agent.tar.gz edu-fde-agent/

  # 上传到服务器
  scp edu-fde-agent.tar.gz root@[服务器IP]:/home/

服务器操作：
  # 解压
  cd /home
  tar -xzf edu-fde-agent.tar.gz
  cd edu-fde-agent

  # 安装Docker（如果没有）
  curl -fsSL https://get.docker.com | sh

  # 配置环境变量
  cp .env.example .env
  vim .env  # 填入真实的API Key等

  # 构建镜像
  docker build -t edu-fde-agent .

  # 启动容器
  docker run -d \
    -p 8000:8000 \
    --env-file .env \
    --name edu-fde-agent \
    edu-fde-agent

  # 查看是否启动成功
  docker ps
  docker logs edu-fde-agent

方式二：使用Git（如果代码在GitHub/Gitee上）
  git clone [仓库地址]
  cd edu-fde-agent
  # 后续步骤同上
```

**关键节点指引：**

```
⚠️ 关键节点1：.env文件不要上传到Git
   .env包含API Key等敏感信息
   确认.gitignore里有.env
   服务器上手动创建.env并填写

⚠️ 关键节点2：docker run的-d参数
   -d表示后台运行（daemon）
   不加-d的话关闭终端服务就停了

⚠️ 关键节点3：端口映射
   -p 8000:8000 表示把容器的8000端口映射到服务器的8000端口
   左边是服务器端口，右边是容器端口
   确保服务器安全组/防火墙开放了对应端口
```

**验收标准：**
docker ps显示容器状态为Up，服务器IP:端口可以访问即完成。

### STEP 4：Nginx反向代理

**教学目标：**
配置Nginx，让服务通过标准的80端口或域名访问，而不是暴露具体端口号。

**核心概念：**

```
为什么需要Nginx？

没有Nginx：
  用户访问 http://123.456.789.0:8000
  · 暴露了具体端口
  · 不支持域名
  · 不支持HTTPS

有了Nginx：
  用户访问 http://123.456.789.0 或 http://yourdomain.com
  Nginx在后台把请求转发到8000端口
  · 端口对用户透明
  · 支持域名绑定
  · 可以配置HTTPS
```

**Nginx配置模板（含填空）：**

```nginx
server {
    listen 80;

    # 学生需要填写：服务器IP地址或域名
    # 如果没有域名，填服务器IP
    server_name _____________;

    location / {
        # 学生需要填写：转发到本地的哪个端口
        # 提示：你的应用运行在8000端口
        proxy_pass http://localhost:_____________;

        # 以下配置平台已提供，学生不需要修改
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

        # 支持流式输出（AI应用常用）
        proxy_buffering off;
        proxy_read_timeout 300s;
    }
}

# [查看原理：Nginx配置各字段含义 ▼]
# · listen 80：监听80端口（HTTP默认端口）
# · server_name：匹配哪些请求（IP或域名）
# · location /：匹配所有路径
# · proxy_pass：把请求转发到哪里
# · proxy_buffering off：关闭缓冲，支持流式输出
# · proxy_read_timeout：等待后端响应的超时时间
```

**安装和启动Nginx：**

```bash
# 安装Nginx
apt update && apt install -y nginx

# 把配置文件放到正确位置
cp edu-fde.conf /etc/nginx/sites-available/edu-fde
ln -s /etc/nginx/sites-available/edu-fde /etc/nginx/sites-enabled/

# 删除默认配置（避免冲突）
rm /etc/nginx/sites-enabled/default

# 测试配置是否正确
nginx -t

# 启动/重启Nginx
systemctl restart nginx
systemctl enable nginx  # 设置开机自启
```

**验收标准：**
通过服务器IP（不带端口号）可以正常访问应用即完成。

### STEP 5：稳定性保障

**教学目标：**
让学生了解如何保证服务在异常情况下自动恢复，以及如何查看日志定位问题。

**自动重启配置：**

```bash
# 停止并删除之前的容器
docker stop edu-fde-agent
docker rm edu-fde-agent

# 重新启动，加上自动重启策略
docker run -d \
  -p 8000:8000 \
  --env-file .env \
  --name edu-fde-agent \
  --restart unless-stopped \  # 关键：除非手动停止，否则自动重启
  edu-fde-agent

# --restart的几个选项：
# no：不自动重启（默认）
# always：总是自动重启
# unless-stopped：除非手动停止，否则自动重启（推荐）
# on-failure：只在容器异常退出时重启
```

**日志查看：**

```bash
# 查看容器日志
docker logs edu-fde-agent

# 实时查看最新日志（类似tail -f）
docker logs -f edu-fde-agent

# 只看最近50行
docker logs --tail 50 edu-fde-agent

# 查看Nginx访问日志
tail -f /var/log/nginx/access.log

# 查看Nginx错误日志
tail -f /var/log/nginx/error.log
```

**模拟故障演练：**

```
练习一：模拟服务崩溃后自动恢复
  1. 手动kill掉容器内的进程
     docker exec edu-fde-agent kill 1
  2. 等待几秒，观察容器状态
     docker ps
  3. 你应该看到：容器自动重启，状态重新变为Up

练习二：通过日志定位问题
  1. 故意在.env里把API Key改错
  2. 重启容器
  3. 查看日志，找到错误信息
  4. 根据错误信息修复问题
```

## 六、界面设计要点

### 整体布局

```
┌─────────────────────────────────────────────────────────┐
│  顶部：阶段进度 | 当前路径 | 当前步骤                    │
├──────────────────┬──────────────────────────────────────┤
│                  │                                      │
│  左侧面板        │  右侧主内容区                         │
│                  │                                      │
│  · 步骤进度树    │  操作说明和指引                       │
│  · 命令速查表    │  代码块（可一键复制）                  │
│   （常驻可查）   │  填空模板                             │
│                  │  完成验证说明                         │
│  · 常见问题      │                                      │
│   （折叠展开）   │  提交区：                            │
│                  │  · 服务器地址输入                     │
│                  │  · 验收测试触发按钮                   │
│                  │  · 交付文档提交                       │
├──────────────────┴──────────────────────────────────────┤
│  底部：Docker官方文档 | Nginx文档 | 云服务商控制台        │
└─────────────────────────────────────────────────────────┘
```

### 关键界面细节

**代码块设计：**
所有命令和代码块都有一键复制按钮，学生不需要手动输入长命令，减少因打字错误导致的卡壳。

**常见问题库：**
整理部署过程中最高频的10个报错，学生遇到问题可以先查这里：
- 端口被占用怎么办
- docker build失败常见原因
- SSH连接超时怎么处理
- 服务器安全组怎么配置
- Nginx配置测试失败怎么排查

**验收测试实时反馈：**

```
正在验收...

✅ 服务可正常访问
✅ 健康检查接口正常
✅ 标准问题1回答正确
✅ 标准问题2回答正确
⏳ 标准问题3测试中...
```

逐条显示测试进度，不是等全部完成才显示结果，让学生有实时反馈感。

## 七、待确认事项

> 阶段五设计已达成共识，以下为开发阶段需进一步细化的技术决策

1. **健康检查接口**：代码路径的LangGraph应用需要实现一个/health接口，需要在阶段四的脚手架中预置好
2. **验收测试的触发方式**：平台主动访问学生提交的服务器地址，需要考虑学生服务器的网络安全组配置是否允许平台IP访问
3. **交付文档的存储**：学生提交的交付文档是否需要持久化存储，供教师后续查看评分
4. **学习画像的生成时机**：是阶段五验收通过后立即生成，还是教师确认后生成
5. **服务器费用问题**：是否需要在平台内给出申请学生优惠的指引，降低学生的使用成本
